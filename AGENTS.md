# Правила работы над POSvpn

Файл для людей и ИИ-агентов. Проект ведётся разными пользователями и в разных
сессиях, поэтому договорённости живут в репозитории, а не в переписке.

## 1. Главное правило: после каждого изменения — релиз

**Любое изменение в проекте заканчивается сборкой exe, сборкой установщика,
коммитом и пушем.** Работа, оставленная «только в файлах» или только в
локальном коммите, не считается сделанной.

Одна команда делает всё:

```powershell
.\release.ps1 "область: результат"
```

Что она делает по шагам:

| Шаг | Действие | Результат |
|---|---|---|
| 1 | `build.ps1` | `out\posvpn-server.exe`, `out\posvpn-client.exe` |
| 2 | `ISCC.exe installer\posvpn-setup.iss` | `installer\out\POSvpn-Setup-<версия>.exe` |
| 3 | `git add -A`, `git commit` | коммит в `main` |
| 4 | `git push origin main` | коммит на GitHub |

Проверка после запуска:

```powershell
git status                      # пусто
git log origin/main..main       # пусто — значит запушено
Get-ChildItem out, installer\out
```

### Если релиз не прошёл

| Симптом | Что делать |
|---|---|
| `ISCC.exe не найден` | Установить Inno Setup 6 (`choco install innosetup`) или прописать путь в `release.ps1`. Не пропускать шаг установщика молча |
| `build cache is required` | Задать `GOCACHE` (например, `$env:GOCACHE="$env:TEMP\posvpn-gocache"`) и повторить |
| Тесты красные | Починить до коммита. Красные тесты не коммитятся и не пушатся |
| Push отклонён | `git pull --rebase origin main`, затем повторить `git push origin main` |
| Установщик не собрался | Исправить `.iss` или окружение; не коммитить «полурелиз» |

### Чего делать нельзя

- Коммитить без сборки exe и установщика.
- Пушить, не проверив `git status` и `git log origin/main..main`.
- Оставлять изменения незакоммиченными «на потом».
- Менять версию в `installer/version.txt` без причины: версия поднимается
  осознанно (заметное изменение или релиз), иначе установщик перезаписывается
  тем же именем.

## 2. Язык

- Документация, комментарии в коде, сообщения коммитов и интерфейс — по-русски.
- Имена пакетов, типов, функций и полей JSON — по-английски.
- Термины: «узел», «сеть», «карта сети», «хаб», «кадр» — как в
  [docs/06-ТЗ.md](docs/06-ТЗ.md).

## 3. Источник правды

1. `docs/` — единственный источник правды. Решение, которого нет в `docs/`,
   не считается принятым.
2. Архитектурные решения (L3, QUIC, свой кадр, адресация `10.77/16`) меняются
   только с записью в [docs/03-архитектура.md](docs/03-архитектура.md) и
   объяснением причины.
3. Новые зависимости фиксируются с версией и обоснованием в
   [docs/04-стек.md](docs/04-стек.md).
4. Требования и их статус — в [docs/06-ТЗ.md](docs/06-ТЗ.md); этапы — в
   [docs/05-план.md](docs/05-план.md).

## 4. Начало сессии

```powershell
git log --oneline -10
git status
go test ./...        # в engine и posvpn-server
```

Затем прочитать `README.md`, `docs/05-план.md`, `docs/06-ТЗ.md`.

## 5. Проверки

| Что | Команда |
|---|---|
| Тесты общих типов | `cd engine; go test ./...` |
| Тесты сервера | `cd posvpn-server; go test ./...` |
| Сборка обоих exe | `.\build.ps1` |
| Полный релиз: exe + установщик + коммит + пуш | `.\release.ps1 "область: результат"` |

`go test ./...` должен быть зелёным до коммита. Новая функция — с тестом.

## 6. Запреты

- Не коммитить секреты: `client.json`, `server.json`, `*.log`, приватные ключи.
- Не менять `10.77.0.0/16` и формат кадра без записи в `docs/03`.
- Не добавлять зависимости «на всякий случай»: только под конкретное требование.
- Не обещать в документах то, чего нет в коде: статус требования — только
  «сделано», «в работе», «план».
- Не оставлять изменения без коммита и пуша.

## 7. Структура

| Путь | Что это |
|---|---|
| `engine/` | Общие типы, адресация, секреты, ключи, тесты |
| `posvpn-server/` | Координатор: API, хранилище, хаб (этап 1) |
| `posvpn-client/` | Клиент: CLI сейчас, служба и GUI — этапы 2–3 |
| `installer/` | Inno Setup, версия продукта |
| `docs/` | Документация: обзор, аналоги, функционал, архитектура, стек, план, ТЗ, ТЭО, сравнение |
| `research/` | Сырьё разведки, не переписывается задним числом |

## 8. Definition of done

1. Требование из ТЗ выполнено и проверено вручную или тестом.
2. `go test ./...` зелёный.
3. `.\release.ps1 "область: результат"` отработал целиком: exe собран,
   установщик собран, коммит создан, пуш выполнен.
4. Документы обновлены: статус в `README.md`, отметки в `docs/05-план.md`,
   при необходимости — ТЗ и архитектура.
5. `git status` пуст, `git log origin/main..main` пуст.
